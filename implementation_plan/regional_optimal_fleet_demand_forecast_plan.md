# 지역별 일 적정 할당대수·수요예측 모델 구현 계획서

- 문서 상태: 사용자 리뷰 요청본 v1
- 작성 기준일: 2026-08-07
- 구현 상태: 계획 수립 단계이며 모델·배치 소스는 변경하지 않음
- 1차 권장 예측 단위: `예측일 × 캠프(중지역) × 기기구분(자전거/킥보드)`
- 1차 권장 예측 시점: D일 운영계획 수립 시점에 D+1을 예측

## 1. 결론 및 권장 아키텍처

현재 제공 가능한 데이터로 머신러닝 기반의 지역별 일 수요예측과 적정 할당대수 추천 모델을 개발할 수 있다. 다만 과거 데이터에는 실제로 발생한 운행만 있고 공급 부족으로 놓친 수요가 없으므로, v1 결과는 통계적으로 검증된 **수요 대응 권장대수**로 정의한다. 미충족 수요 데이터나 공급 변화 실험 없이 이를 절대적인 최적대수로 표현하지 않는다.

권장 구조는 하나의 모델이 적정대수를 직접 맞히게 하는 방식이 아니라 다음 세 계층을 분리하는 방식이다.

1. **수요예측 계층**: 지역별 운행수와 매출의 P50/P80/P90 예측
2. **운영역량 계층**: 가동률과 운행 기기당 처리량을 예측하고 정상 생산성 범위를 산출
3. **의사결정 계층**: 예측 수요, 월 목표 매출, 총 보유대수와 운영 제약을 결합하여 최소·권장·안전 할당대수 계산

이 구조는 목표 매출 변경, 안전 수준 변경, 총 보유대수 제약 변경 시 모델을 다시 학습하지 않고 시나리오를 재계산할 수 있다.

## 2. 모델링 방식 대안

| 대안 | 구성 | 성능 잠재력 | 유지보수·설명력 | 필요 자원 | 판단 |
|---|---|---:|---:|---:|---|
| A. 적정대수 직접 예측 | 과거 자료로 적정대수 대리 라벨을 만든 뒤 단일 회귀모델 학습 | 중간 | 낮음. 대리 라벨의 오류를 그대로 학습 | 낮음 | 기준선 또는 비교모델로만 사용 |
| B. 수요·운영역량 예측 후 최적화 | 운행수·매출·가동률·생산성을 각각 예측하고 규칙/최적화 계층에서 할당대수 산출 | 높음 | 높음. 결과 원인과 제약을 분리 가능 | 중간 | **v1 권장안** |
| C. 공급반응·인과모델 | 할당대수 증감에 따른 추가 운행·매출 효과를 추정하고 전체 기기를 최적 배분 | 가장 높음 | 중간. 실험 또는 자연실험 설계 필요 | 높음 | 미충족 수요와 운영 실험 확보 후 v2 |

v1은 B안을 운영 후보로 구현하고 A안을 비교 기준선으로 유지한다. C안은 지역별 공급 증감 실험, 예약 실패·검색·미배정 수요 또는 충분한 자연실험 데이터가 확보된 이후 진행한다.

## 3. 목표와 범위

### 3.1 목표

- 지역·기기구분별 D+1 운행수와 매출의 확률 분포를 예측한다.
- 월 목표 매출의 지역별·일별 필요 매출과 필요 운행수를 계산한다.
- 가동률과 생산성의 보수적 추정치를 이용해 최소·권장·안전 할당대수를 제공한다.
- 현재 할당대수 대비 증감 권고와 목표 달성 가능성 상태를 함께 제공한다.
- 모델의 예측 정확도뿐 아니라 부족대수, 유휴대수, 목표 달성 위험을 시간순 백테스트로 검증한다.

### 3.2 v1 제외 범위

- 공휴일, 지역 축제, 콘서트 등 이벤트 피처는 현재 제외한다.
- 배치존별 최종 배치 수량 최적화는 하지 않는다. 배치존 데이터는 캠프 단위 선행 피처로 집계한다.
- 기기 이동 비용, 창고·정비 처리량, 캠프 간 이동 가능 대수를 모르는 상태에서 전사 총량 최적화를 확정하지 않는다.
- 현재 데이터만으로 관측되지 않은 잠재수요를 사실값처럼 복원하지 않는다.
- 모델이 제안한 대수를 자동으로 운영 시스템에 반영하지 않는다. v1은 리포트 및 섀도 운영까지만 수행한다.

## 4. 핵심 지표 정의

기본 집계 단위는 `date × middle_region_id × device_type`으로 고정한다. 현재 추출물에 안정적인 중지역 ID가 없는 데이터셋은 지역 차원 테이블을 통해 ID를 부여한다.

| 지표 | 정의 | 사용 목적 | 주의사항 |
|---|---|---|---|
| 할당대수 | 해당 지역·기기구분의 운영 대상 재고 | 의사결정 변수 및 과거 공급량 | 스냅샷인지 일중 집계인지 원천 정의 확인 필요 |
| 운행대수 | 해당 일자에 1회 이상 운행한 고유 기기수 | 가동률·생산성 산출 | 현재 소지역 합산 시 동일 기기 중복 가능성 검증 필요 |
| 운행수 | 완료된 총 운행 건수 | 주 수요 타깃 | 공급 부족 시 잠재수요보다 작을 수 있음 |
| 순매출 | `(calculated_pay_amount + calculated_out_of_area_charge) / 1.1` 합계 | 매출예측 및 목표 비교 | 목표 매출의 부가세·환불·매출 범위와 일치 여부 확인 필요 |
| 가동률 | `고유 운행대수 / 기준 할당대수` | 운영역량 피처·예측 타깃 | 반드시 0~1이 되는 집계 정의를 먼저 확정 |
| 운행 기기당 운행수 | `운행수 / 고유 운행대수` | 생산성 추정 | 운행대수 0일은 결측으로 처리 |
| 할당 기기당 운행수 | `운행수 / 할당대수` | 공급 생산성 보조지표 | 수요와 공급의 영향을 동시에 받음 |
| 배치 흐름 출루율 | `당일 출루수 / 당일 배치수` | 운영 흐름 보조지표 | 동일 배치 코호트가 아니므로 100% 초과 가능 |
| n시간 내 출루율 | 동일 배치 코호트 중 n시간 내 출루한 비율 | 배치 품질 피처 | 미출루 건을 결측이 아닌 검열 자료로 처리 |
| n시간 미사용률 | `deactivate_nh_count / total_vehicle_count` | 장기 미사용 재고 피처 | 예측일에는 D-1 이전 값만 사용 |

### 5.1 표본 점검에서 확인한 선행 이슈

2026-08-06 자료를 캠프·기기구분으로 합산한 표본 점검 결과 다음 현상이 확인되었다.

- 일부 캠프에서 `운행대수 > 할당대수`가 발생하여 계산 가동률이 100%를 초과했다.
- 배치존 자료를 캠프·기종으로 합산했을 때 일부 그룹에서 `출루수 > 배치수`가 발생했다.
- 출루시간 자료에는 아직 출루하지 않아 `출루까지 시간`이 없는 기기가 존재했다.
- 24/48/72시간 미사용 대수는 표본에서 `72h ≤ 48h ≤ 24h ≤ 총기기수` 관계를 만족했다.

첫 두 현상은 단순 오류일 수도 있지만, 지역 간 이동 기기의 중복 집계와 서로 다른 날짜 코호트의 배치·출루 흐름을 비교한 결과일 수도 있다. 따라서 값을 임의로 100%로 잘라 사용하지 않고 원천 정의와 고유 기기 기준을 확인한다.

## 6. 데이터 계약 및 정합성 설계

### 6.1 표준 키

- 날짜: KST 기준 `YYYY-MM-DD`
- 지역: 안정적인 `middle_region_id`와 표시용 `middle_region_name`
- 기기: 공통 `device_type ∈ {bicycle, scooter}`
- 예측 기준시각: `as_of_timestamp`
- 예측 대상일: `forecast_date`

지역명으로 직접 조인하는 것은 임시 수단으로만 허용한다. 추출 쿼리에는 가능한 경우 중지역 ID, 소지역 ID, 배치존 ID를 함께 저장한다. 명칭 변경 이력은 유효 시작일·종료일이 있는 지역 차원 테이블로 관리하며, 매핑되지 않은 지역을 유사 문자열로 자동 연결하지 않는다.

### 6.2 날짜와 코호트 기준

- 모든 DB 시간은 KST로 변환한 뒤 날짜를 확정한다.
- 배치 건의 기준일은 `deployed_at`으로 통일한다.
- 출루까지 시간은 `released_at - deployed_at`을 기준으로 재검토한다.
- `1/3/6/12/24시간 내 출루율`은 동일 배치일 코호트로 계산한다.
- 24시간 지표는 24시간 관측 창이 끝난 코호트만 피처에 사용한다.
- 당일 배치수와 당일 출루수의 비율은 `daily_flow_release_ratio`로 별도 명명하고 코호트 전환율로 해석하지 않는다.

### 6.3 필수 검증 규칙

- 표준 키 중복 0건
- 할당대수·운행대수·운행수·매출·강수량의 결측 및 음수 검사
- 할당대수 0일의 비율 계산 금지 및 명시적 상태값 부여
- 고유 기기 기준 가동률이 0~1 범위인지 검사
- `72h 미사용 ≤ 48h 미사용 ≤ 24h 미사용 ≤ 총기기수` 검사
- 배치·출루시간 음수 검사 및 미출루 상태 보존
- 지역·기기 매핑 누락 목록과 영향 행 수 출력
- 데이터 소스별 일자·지역 커버리지와 전일 대비 행 수 급변 로그
- 일별 통계의 운행수·매출 합계가 기존 운영 리포트와 일치하는지 표본 대사
- 목표 매출과 실제 매출의 부가세, 환불, 지역 범위, 기기 범위를 동일 기준으로 맞춤

핵심 일별 통계가 없거나 표준 키가 중복되면 해당 예측 배치는 실패 처리한다. 보조 피처가 누락된 경우 0으로 조용히 대체하지 않고 결측 플래그와 대체 경로를 기록한다.

## 7. 예측 시점 기준 피처 설계

모든 학습행은 `forecast_date` 직전의 `as_of_timestamp`에서 실제로 알 수 있었던 값만 포함한다. rolling 계산은 반드시 `shift(1)` 이후 수행한다.

### 7.1 사전에 알려진 피처

- 지역 ID, 기기구분
- 요일, 주말 여부, 월, 연중 주차, 월초·월말, 계절
- 예측 기상의 일 총 강수량, 시간당 평균 강수량
- 추후 기상 원천 확장 시 평균/최저/최고기온, 적설, 풍속, 날씨코드
- 예측 시점에 공표되어 있던 월 목표 매출과 목표 버전

공휴일·축제·콘서트 피처는 v1에서 생성하지 않는다.

### 7.2 과거 수요·매출 피처

- 운행수·매출·건당 매출의 lag 1/2/7/14/28
- 동일 요일 lag 7/14/21/28
- 7/14/28일 이동평균, 중앙값, 표준편차, 추세
- 강수 유무별 과거 운행수와 매출 반응
- 지역·기기구분별 장기 수준과 최근 수준의 비율

### 7.3 가동률·운영 피처

- 검증된 가동률의 lag 1/7/14/28 및 7/14/28일 이동통계
- 운행 기기당 운행수와 할당 기기당 운행수의 지연값
- 배치수·출루수·배치 흐름 출루율의 지연값
- 동일 코호트의 1/3/6/12/24시간 내 출루율
- 출루까지 시간의 P50/P75/P90과 미출루 비율
- 24/48/72시간 미사용률과 변화량
- 배치존별 지표를 캠프 단위로 집계한 평균, 가중평균, 하위 분위수, 저효율 배치존 비중

예측 대상일의 실제 가동률, 출루율, 미사용률은 결과가 발생한 뒤에만 알 수 있으므로 피처로 사용하지 않는다. 별도 운영역량 모델이 예측한 당일 가동률만 할당대수 계산에 사용한다.

### 7.4 월 목표 매출 피처와 제약값

월 목표 매출은 수요를 직접 발생시키는 변수가 아니므로 두 용도로 분리한다.

**머신러닝 후보 피처**

- 지역 월 목표 매출
- D-1까지의 월 누적 실매출
- 잔여 목표 매출
- 잔여 일수와 일평균 필요 매출
- D-1 기준 목표 달성률과 목표 격차율
- 전년 또는 기준기간 실적 대비 목표 성장률(비교 가능한 기간이 있을 때만)

목표 피처 포함 모델과 제외 모델을 동일한 rolling backtest로 비교한다. 목표 피처가 일반화 성능을 개선하지 못하거나 특정 월의 사후 수정값 때문에 누수가 발생하면 수요모델에서는 제외하되 의사결정 계층의 제약값으로는 유지한다.

**의사결정 제약값**

월 잔여 목표를 남은 날짜의 기본 매출예측 비중으로 배분한다.

```text
일 목표 매출 = 월 잔여 목표 매출 × 해당 일 기본 예측매출 / 남은 기간 기본 예측매출 합계
목표 필요 운행수 = 일 목표 매출 / 예측 건당 매출
```

예측일 당시 공개된 목표 버전과 D-1까지의 실적만 사용한다. 월중 목표 변경 시 `effective_from`, `published_at`, `version`을 저장하여 백테스트에서도 당시 알 수 있었던 목표만 재현한다.

### 7.5 전사 목표만 존재할 때의 지역 배분 대안

| 대안 | 방식 | 장점 | 한계 |
|---|---|---|---|
| 사업부 제공 지역 가중치 | 운영 조직이 월별 지역 목표 비중을 제공 | 책임과 해석이 명확 | 별도 관리 필요 |
| 기본 매출예측 비중 | 지역별 목표 없는 경우 예상 매출 비중으로 자동 배분 | 수요 계절성 반영, 자동화 용이 | 목표와 예측이 일부 순환할 수 있음 |
| 최근 실적 비중 | 최근 8~12주 매출 비중으로 배분 | 단순하고 안정적 | 성장 지역과 신규 지역을 과소평가 |

지역별 목표가 없다면 **기본 매출예측 비중**을 권장하되, 배분 근거와 비중을 결과에 함께 노출한다. 신규 지역이나 전략 지역은 사업부 가중치로 덮어쓸 수 있게 한다.

## 8. 기상 데이터 설계

### 8.1 과거 기상

현재 추출물의 `일 총 강수량`, `시간당 평균 강수량`을 사용한다. 지역명 대신 중지역 ID를 포함하도록 추출 스키마를 보완한다. 추가 날씨 피처가 필요하면 원천 테이블 보유 컬럼을 먼저 확인하고, 학습·예측 양쪽에서 동일하게 제공할 수 있는 변수만 채택한다.

### 8.2 미래 기상 API

공급자와 무관하게 다음 공통 스키마로 저장하는 어댑터를 구현한다.

```text
forecast_date, middle_region_id, latitude, longitude,
precipitation_sum, precipitation_mean, temperature_mean,
weather_code, issued_at, lead_days, provider, provider_model
```

- 지역별 대표 좌표는 캠프 관할 폴리곤 중심점 또는 승인된 대표 좌표를 사용한다.
- API 응답·타임아웃·상태코드를 기록하되 인증키는 로그에 남기지 않는다.
- 예보 원본을 발표시각별로 저장하여 과거 백테스트에서 미래의 실황 날씨를 사용하지 않는다.
- 예보가 없던 과거 구간은 실황 날씨를 사용한 `weather_oracle` 평가와 날씨를 제외한 평가를 분리한다.
- 운영 중 API 실패 시 최근 정상 예보, 지역·월별 평년값 순으로 대체하고 `weather_fallback_level`을 출력한다.

기상 API 공급자는 다음 중 하나를 검토한다.

1. 국내 공공 기상 API: 국내 격자 적합성과 출처 신뢰도가 높지만 인증·격자 변환·운영 관리가 필요하다.
2. 범용 기상 API: 연동이 단순하지만 지역 정확도, 이용조건, 호출 제한을 검증해야 한다.
3. 상용 기상 API: SLA와 지원이 있으나 비용과 공급자 종속성이 증가한다.

공급자 선정 전에는 인터페이스와 로컬 저장 구조까지만 확정하여 교체 가능하게 유지한다.

## 9. 모델 상세 설계

### 9.1 학습 데이터 구조

한 행은 `forecast_date × middle_region_id × device_type`이다. 지역별 개별 모델은 표본이 부족해질 수 있으므로 모든 지역을 함께 학습하는 글로벌 모델을 기본으로 한다. 지역 ID와 기기구분을 범주 피처로 사용하고, 신규·희소 지역에는 상위 지역 통계와 전체 평균으로 후퇴하는 계층적 피처를 제공한다.

가용 기간이 서로 다르므로 다음 두 데이터셋을 병행한다.

- **Core 데이터셋**: 2025-01-01 이후 일별 통계와 날짜 피처 중심
- **Enhanced 데이터셋**: 2026-01-01 이후 기상·출루시간·미사용 통계를 추가

우선 과거 기상과 운영 자료를 2025-01-01까지 백필할 수 있는지 확인한다. 백필할 수 없다면 전체 기간을 억지로 축소하지 않고 Core 모델과 Enhanced challenger를 각각 평가한다.

### 9.2 예측 타깃

| 모델 | 타깃 | 출력 |
|---|---|---|
| 수요모델 | 일 운행수 | P50/P80/P90 |
| 매출모델 | 일 순매출 또는 건당 매출 | P50/P80/P90 또는 중앙값 |
| 가동률모델 | 검증된 고유 운행대수/기준 할당대수 | 예측값과 하한 |
| 생산성모델 | 고유 운행 기기당 운행수 | 예측값과 하한 |

1차 후보 알고리즘은 현재 환경에 이미 존재하는 XGBoost 기반 글로벌 모델이다. 현재 로컬 환경의 XGBoost 3.2.0은 분위수 회귀 후보로 검증할 수 있다. 계절 단순 기준선, 현재 저장소의 Prophet+XGBoost 구조, XGBoost 단독 모델을 함께 비교하며 기존 매출예측 코드를 그대로 복제하지 않고 공통 로직을 유틸리티로 분리한다.

### 9.3 알고리즘 후보 비교

| 후보 | 장점 | 한계 | 사용 계획 |
|---|---|---|---|
| XGBoost | 현재 환경·코드 재사용, 비선형 상호작용과 분위수 예측 가능 | 범주형·시계열 피처를 명시적으로 설계해야 함 | **주 모델 후보** |
| CatBoost | 지역 등 범주형 처리와 소표본 범주에 강함 | 새 의존성과 별도 운영 검증 필요 | challenger |
| Prophet+잔차모델 | 추세·계절 설명이 쉬움 | 지역 수가 많을 때 모델 수와 유지비 증가 | 계절 기준선/비교모델 |

최종 채택은 시간순 백테스트 결과, 추론시간, 설치 재현성으로 결정한다. 채택 버전은 의존성 선언 파일에 고정한다.

## 10. 적정 할당대수 산출 로직

적정대수는 모델의 직접 타깃이 아니라 예측값을 입력으로 받는 계산 결과다.

```text
예측 일 처리량 = 예측 가동률 하한 × 예측 운행기기당 운행수 하한
수요 대응 대수(p) = ceil(운행수 예측 Qp / 예측 일 처리량)
```

- 최소대수: P50 수요 기준
- 권장대수: P80 수요 기준
- 안전대수: P90 수요 기준

월 목표 매출은 다음과 같이 결합한다.

```text
목표 필요 운행수 = 일 목표 매출 / 예측 건당 매출
목표 대응 대수 = ceil(목표 필요 운행수 / 예측 일 처리량)
잠정 권장대수 = max(P80 수요 대응 대수, 목표 대응 대수)
```

목표 필요 운행수가 P90 예측수요를 초과하면 기기를 더 배치한다고 매출이 자동 발생한다고 가정하지 않는다. 이 경우 권장대수를 P90 수요 대응 범위 내로 제한하고 `target_demand_insufficient` 상태와 예상 매출 부족액을 출력한다. 프로모션·가격·영업 활동 등 수요 창출 수단이 별도로 필요하다는 의미다.

최종 권장대수에는 다음 운영 제약을 적용할 수 있게 설계한다.

- 지역·기기구분별 최소/최대 보유대수
- 전일 대비 이동 가능한 최대 증감대수
- 정비·충전·고장으로 실제 할당할 수 없는 대수
- 캠프 간 이동 가능한 총량과 이동 비용
- 전사 또는 센터별 총 가용 기기수

총 가용대수 제약이 제공되지 않으면 v1은 지역별 독립 필요대수와 전사 합계를 출력하되 실행 가능한 최종 배분이라고 표시하지 않는다. 제약이 제공되면 예상 매출 기여와 부족 위험을 목적함수로 하는 포트폴리오 최적화 계층을 추가한다.

## 11. 학습·검증 설계

### 11.1 기준선

- 전일 값
- 최근 7일 평균
- 최근 4주 동일 요일 평균
- 지역·기기구분·요일별 중앙값과 P80/P90
- 현재 할당대수를 유지하는 정책

복잡한 모델은 가장 강한 기준선보다 안정적으로 좋아야 채택한다.

### 11.2 시간순 백테스트

- 랜덤 분할을 금지하고 expanding-window 또는 rolling-window를 사용한다.
- 각 fold의 학습 종료일 이후 자료로 피처를 만들지 않는다.
- 월 목표 변경 이력과 기상 발표시각을 `as-of` 기준으로 재현한다.
- 전체 지표뿐 아니라 지역, 기기구분, 강수 구간, 요일, 수요 상·하위 구간별 결과를 평가한다.
- 신규 지역과 데이터 희소 지역을 별도 슬라이스로 평가한다.

### 11.3 모델 평가 지표

- 운행수·매출: MAE, WAPE, RMSLE
- 확률예측: pinball loss, P80/P90 실제 포함률
- 가동률·생산성: MAE와 범위 위반률
- 월 목표: 예상 달성률 오차, 부족액 오차, 달성 가능성 calibration
- 운영 시뮬레이션: 부족 추정대수, 유휴 추정대수, 과소·과다 권고일 비율, 현재 정책 대비 총 할당 변화

실제 적정대수 정답은 존재하지 않으므로 과거 실제 할당대수와의 차이를 정확도로 해석하지 않는다. 과거 수요를 처리할 수 있었는지와 유휴·부족 비용의 정책 시뮬레이션으로 평가한다.

### 11.4 피처 기여도 검증

다음 순서로 ablation test를 수행한다.

1. 날짜·과거 수요만 사용
2. 강수·기상 추가
3. 목표 매출 관련 피처 추가
4. 가동률·미사용률 추가
5. 배치존·출루시간 피처 추가

각 그룹이 out-of-time 성능과 권고 안정성을 개선하는지 측정한다. 목표 매출이나 가동률이 중요 피처로 나타났다는 이유만으로 인과효과라고 해석하지 않는다.

### 11.5 초기 승인 기준안

- 표준 키 중복 0건, 미매핑 지역·기기 0건
- 핵심 입력 데이터 일별 커버리지 98% 이상
- 운행수·매출 WAPE가 가장 강한 기준선보다 전체 기준 5% 이상 개선
- P80/P90 예측의 실제 포함률이 명목 수준에서 ±5%p 이내
- 특정 주요 지역·기기구분에서 반복적인 과소예측이 없어야 함
- 권장대수 정책이 현재 정책 대비 부족 위험을 악화시키지 않으면서 유휴대수 또는 총 할당대수를 개선
- 오류·대체 데이터·모델 버전만으로 동일 결과를 재현 가능

수치는 첫 데이터 진단 결과와 운영 비용 정의를 검토한 뒤 최종 확정한다.

## 13. 결과 데이터 계약

최종 일별 출력은 최소 다음 컬럼을 가진다.

```text
generated_at, as_of_timestamp, forecast_date,
middle_region_id, middle_region_name, device_type,
trip_p50, trip_p80, trip_p90,

current_assigned_count, recommended_delta,
weather_fallback_level, data_quality_status,
model_version, feature_version, target_version,

```

주요 `reason_codes` 예시는 `rain_risk`, `weekend_uplift`, `recent_demand_down`, `low_activation_rate`, `high_inactive_48h`, `target_gap`, `target_demand_insufficient`, `weather_fallback`이다.

## 14. 예외 처리·로깅·운영 안전성

- 모든 DB·파일·API 호출은 대상 날짜, 지역, 소스, 예외 유형을 포함해 로깅한다.
- 핵심 일별 통계 또는 모델 아티팩트가 없으면 해당 범위의 권고 생성을 중단한다.
- 목표 매출이 없으면 수요 기반 권고는 생성하되 `target_unavailable`로 표시한다.
- 기상 API 장애 시 정의된 대체 경로를 사용하고 대체 수준을 결과에 기록한다.
- 보조 운영 피처가 없으면 Core 모델로 후퇴하고 `model_fallback`을 기록한다.
- 결측값을 0으로 처리할 수 있는 것은 실제 의미가 0으로 확정된 컬럼에 한정한다.
- 비정상 대수나 NaN/무한대가 최종 결과에 있으면 파일 저장·전송 전에 검증 실패로 종료한다.
- 동일 `as_of_timestamp × forecast_date × region × device_type × model_version` 실행은 멱등하게 저장한다.
- 외부 리포트 전송과 실제 운영 반영은 사용자 승인 전 비활성 상태로 유지한다.

## 15. 단계별 구현 계획과 검증 게이트

### Phase 0. 지표·운영 계약 확정

- 할당대수와 운행대수의 원천 집계 정의 확인
- 중지역·기기구분 표준 키 확정
- 목표 매출의 지역 단위와 회계 기준 확정
- 예측 기준시각, 예측 기간, P80/P90 정책 확정
- 총 보유대수와 이동 제약의 제공 가능 여부 확인

**게이트:** 핵심 지표 정의와 조인 키를 사용자 승인 없이 임의 확정하지 않는다.

### Phase 1. 데이터 진단과 표준 Feature Mart

- 전체 기간 파티션, 스키마, 지역 커버리지 점검
- 가동률 100% 초과 원인과 중복 기기 집계 여부 검증
- 배치·출루 코호트 쿼리 및 출루시간 기준 정비 계획 확정
- 공통 Parquet 로더, 지역 매핑, 품질검사 구현
- point-in-time 기준의 Core/Enhanced feature mart 생성
- 가능한 소스는 2025-01-01까지 백필

**게이트:** 표준 키 중복, 지역 매핑 누락, 날짜 누수 검사를 통과한 후 모델링으로 이동한다.

### Phase 2. 기준선과 수요·매출 모델

- 계절 기준선 구현
- XGBoost 운행수 P50/P80/P90 모델 구현
- 매출 또는 건당 매출 모델 구현
- 목표 매출 피처 포함/제외 ablation test
- 모델·피처 버전과 학습 로그 저장

**게이트:** 시간순 백테스트에서 기준선 대비 개선과 분위수 calibration을 통과해야 한다.

### Phase 3. 운영역량 모델과 적정대수 계산

- 가동률 정의가 확정된 뒤 가동률 예측모델 구현
- 생산성 하한과 안정 구간 산출
- 최소·권장·안전대수 계산기 구현
- 목표 매출의 일별 분배와 달성 가능성 상태 구현
- 총량 제약이 있으면 포트폴리오 최적화 추가

**게이트:** 0대·결측·극단 날씨·신규 지역 시나리오 테스트와 물리적 범위 검사를 통과해야 한다.

### Phase 4. 정책 백테스트와 설명 리포트

- 과거 날짜별 D+1 재예측
- 현재 할당 정책 대비 부족·유휴·목표 매출 시뮬레이션
- 지역·기기·강수 구간별 오류 분석
- SHAP 또는 피처 기여도와 reason code 생성
- 결과 Parquet/CSV 및 리뷰 리포트 생성

**게이트:** 모델 정확도와 운영 정책 지표를 함께 승인받는다.

### Phase 5. 섀도 운영

- 최소 4주간 매일 D+1 권고를 생성하되 실제 할당에는 자동 반영하지 않음
- 기상 API 장애, 지역 변경, 목표 변경, 데이터 지연을 관측
- 예측 편향과 권고 변동폭을 주간 리뷰
- 운영자 판단과 차이가 큰 사례의 원인을 기록

**게이트:** 섀도 결과와 운영 제약을 재검토한 뒤 제한된 지역의 수동 파일럿 여부를 결정한다.

## 17. 다음 리뷰에서 확정할 항목

1. 1차 예측 단위를 `캠프(중지역) × 자전거/킥보드`로 확정할지 여부
2. D+1을 주 운영 예측으로 하고 D+7을 참고 전망으로 제공할지 여부
3. `할당대수`와 `운행대수`의 정확한 원천 정의 및 100% 초과 가능 사유
4. 월 목표 매출이 전사·센터·캠프·기기구분 중 어느 수준까지 제공되는지
5. 목표 매출과 현재 `revenue`의 부가세·환불·서비스 범위가 동일한지
6. 지역별 목표가 없을 때 기본 매출예측 비중으로 배분해도 되는지
7. 권장대수의 위험 수준을 P80으로 시작할지, P90으로 시작할지
8. 센터·캠프별 총 보유대수, 최소/최대 대수, 일 이동 한도를 제공할 수 있는지
9. 미래 기상 API 공급자와 예보 수집 기준시각
10. 가동률 고유 기기 집계를 위해 원천 주문 또는 기기 ID 단위 데이터를 추가 조회할 수 있는지

위 항목 승인 후 Phase 0의 데이터 계약서를 먼저 확정하고 Phase 1 구현으로 진행한다.
